# 工作台界面规范

这份文档是工作台（`easel` 窗口，源码 `workbench/main.cpp`）界面的**依据**，不是设计心得。
写界面、改界面、review 界面都对着这里的条目逐条核对；条目之外的东西一律不许出现在界面上。

适用范围：只管 GUI。无头命令行（`--new` / `--build` / `--run` / `--package` / `--export` /
`--clean`）不经过这里的任何一条布局规则，但**用词**（第 1 节）两边必须一致。

工作台要回答的三件事，界面从上到下的顺序就是这三件事：

1. 现在是哪个工程
2. 点哪里开始
3. 刚才发生了什么（结论），以及凭什么这么说（证据）

## 0. 先读这一条：界面上不许出现内置字体没有的字符

> **`✔ ✖ ▶ ■ ⊙ ⤡ ⌃ √ ☐ ▸ ↑ ↓ ⚠ ● ◆` 这些符号一个都不能用。**
> 内置字体子集（`scripts/make_font_subset.py`）里**没有**它们，界面上会变成一串豆腐块（□）。
>
> 子集只含这三类：
> 1. ASCII（`0x20`–`0x7E`）；
> 2. CJK 基本区 `U+4E00`–`U+9FA5`（汉字全要）；
> 3. 一小串中文标点，**只有这些**：
>    `　、。，．；：？！…—～《》「」『』（）【】·’‘“”￥°±×÷≤≥≈∞`
>
> **规则：往界面加任何"既不是 ASCII、也不是汉字"的字符之前，先去 `scripts/make_font_subset.py`
> 里查它在不在上面三类里。不在就不许用**，没有例外、不靠"我这台机器上能显示"——开发机命中
> 系统字体时符号会正常显示，学生拿到的发布包用的是内置子集，同一份代码在那边就是豆腐块。
>
> 替代办法（本规范后面一律按这三条写）：
> - 状态、结果用**汉字 + 颜色**：`完成` / `失败` / `运行中` / `编译中` / `已停止`。
> - 折叠 / 展开的三角箭头用 `ImGui::ArrowButton()`、`CollapsingHeader`、`TreeNode`——ImGui 自己
>   用矢量画的，不经过字体。
> - 勾选框用 `ImGui::Checkbox`（同样是矢量画的），不要用 `☐` / `☑` 这种字符糊一个。
> - 实在要分隔符，只能用上面第 3 类里真有的（`·` 安全，已在用）。
> - 「产出到哪儿」这种箭头用 ASCII 的 `->`，不要用 `→`（U+2192，不在子集里）。
>
> **本文档和所有讨论稿里的界面草图都不算数**：早期草图用过 `✔ ⊙ ⤡ ⌃ ☐ ▶`，照着画就会踩坑。
> 文档里现在的草图已经全部换成 ASCII 和汉字，以后改草图也按这一条来。

## 1. 用词规则

### 1.1 来源优先级

界面上的每个词都必须能指出出处，**不许自己发明**。按这个顺序找：

1. **Processing** —— 我们对标的库，学生查资料第一个撞到的就是它。
2. **主流 IDE 的通用叫法** —— Visual Studio / VS Code / Xcode / IntelliJ 系，三家以上叫法一致才算"通用"。
3. **其它同类工具** —— Godot、Arduino IDE、Unity 这类。

三档都找不到先例的：**停下来，把这个功能标记出来**，不要硬造一个词。找不到先例通常说明
这个功能本身的概念有问题（切错了颗粒度，或者在暴露实现细节），先改功能，不是先起名字。

### 1.2 已定词表

| 动作 | 界面用词 | 出处 |
|---|---|---|
| 编译并把作品跑起来 | 运行 | Processing 工具栏 Run |
| 掐掉正在跑的东西 | 停止 | Processing 工具栏 Stop |
| 产出能直接运行的程序 | 导出应用程序… | Processing「文件 → 导出应用程序」 |
| 产出能独立编译的完整工程 | 导出工程… | Godot「导出项目」；IDE 通用 |
| 从模板建一个新工程 | 新建工程… | 通用 |
| 打开一个已有工程 | 打开工程… | 通用 |
| 最近用过的工程 | 最近打开 | IDE 通用（File → Open Recent） |
| 删掉可以重新生成的构建产物 | 清理 | **IDE 通用惯例，Processing 没有这个功能**：VS「生成 → 清理解决方案」、Xcode「Product → Clean Build Folder」、Android Studio / IntelliJ「Build → Clean Project」 |
| 编译器 / cmake / 作品的原样输出 | 输出 | VS Code「输出」面板；Processing 叫「控制台」，两者都行，选字少的 |
| 多打一截排障细节 | 详细输出 | MSBuild / Gradle 的 verbose output；VS「输出详细程度」 |
| 清掉输出区的内容 | 清空输出 | VS Code「清除输出」 |
| 窗口压在别的窗口上面 | 始终置顶 | Windows 终端「始终置顶」、VLC「总是置顶」 |
| 把日志区收起来的小窗形态 | 紧凑模式 | Gmail / Slack「紧凑」、Windows 资源管理器「紧凑视图」 |
| 配置 / 偏好 | 设置 | 通用 |
| 打开 `.easel/last-build.log` | 打开日志文件 | 通用（打开的是文件，不是目录） |
| 环境自检 | 环境自检 | 对应 `--doctor`；Arduino IDE / 各家「诊断」类命令 |

**「紧凑模式」是对"精简模式"的改名。** 讨论时用的"精简模式"没有出处，"紧凑 / Compact"有一
大把。同一个东西只能有一个名字：文档、菜单项、`workbench.json` 的键名（`compact`）统一用
紧凑，不要再出现"精简"。

**「工作台」保留。** 它有出处（Eclipse 的主窗口就叫 Workbench / 工作台），而且是这个窗口
的产品名，学生在文档里也一直见到它。

### 1.3 被否掉的词（连同理由，避免下次又冒出来）

| 否掉的词 | 为什么不行 |
|---|---|
| 生成 exe | 三个平台里两个不叫 exe（macOS 是 `.app`，Linux 是裸可执行文件）；而且这是拿文件后缀给功能命名，等于把 Windows 当唯一平台 |
| 导出源码 | "源码"是废话——导出的本来就是源码；真正要区分的是"能直接跑的程序"还是"能自己编的工程" |
| 给别人玩 / 给别人改 | 自创，没有任何出处。看着亲切，但学生查资料时对不上任何资料 |
| 编译并运行 | 把实现步骤当目的说。学生要的是"看见我的作品"，编译是我们的事；Processing 就一个字：Run |
| 精简模式 | 没出处，见 1.2 |
| 打开日志目录 | 它实际打开的是日志**文件**（优先丢给 VS Code），名字和行为不符 |

### 1.4 省略号惯例

- 点下去会**弹对话框**、或者要**选位置**的：标签带省略号（`新建工程…`、`打开工程…`、
  `导出应用程序…`、`导出工程…`、`运行参数…`）。
- 点下去**直接执行**的：不带（`运行`、`停止`、`清空输出`、`清理`、`打开日志文件`、`环境自检`）。
- 开关类菜单项（`详细输出`、`始终置顶`、`紧凑模式`）：不带省略号，带勾选标记。

两个要注意的：

- **`导出应用程序…` 和 `导出工程…` 必须真的有对话框**，才配得上这个省略号。现在这两个
  功能是"点一下就开始编译两分钟"，没有任何预告。按规范各加一个极简确认框（第 6.2 节）。
- **`清理` 不带省略号**：跟 IDE 一致（VS / Xcode / IntelliJ 的 Clean 都不弹确认框），理由见 6.3。

### 1.5 可打印字符的限制

**见第 0 节**，那是全文最硬的一条约束，写在最前面就是为了没人会漏看。
一句话复述：非 ASCII、非汉字的字符，加之前先查 `scripts/make_font_subset.py`；不在子集里就不许用。

已知缺陷：`src/export_project.cpp` 的检查清单用的 `[√]` 就踩了这个坑（`√` 不在子集里）。
那个文件不在本轮改动范围内，记在第 7 节。

### 1.6 内部词汇清单（**本轮只列，不动横幅和日志**）

横幅、摘要行、日志里这些词是对开发者说的，学生看不懂。列在这里，等单独的一次改动处理。
括号里是建议的替代说法。

| 现在的词 | 出现在 | 学生看不懂的点 | 建议 |
|---|---|---|---|
| 预编译 / 预编译包 | 启动横幅、摘要行、速度提示 | 不知道"预编译"是谁编的、编的什么 | 「现成的 Easel 库」；横幅里保留技术词但加一句括号说明 |
| abi | 启动横幅「abi 匹配 / 不匹配」 | 完全是内部概念 | 只在「详细输出」打开时显示；平时说「版本对得上 / 对不上（会慢一点）」 |

| 图形开发包 | 启动横幅（Linux） | 含义模糊 | 「缺少编译要用的图形库」+ 照抄的安装命令（命令已经给了，保留） |
| 工具箱 / 绿色工具箱 | 文档、横幅 | 我们自己的叫法 | 文档里保留（已有解释），界面上不出现 |

## 2. 状态机

状态 = `WB::projectDir` 是否为空 × `WB::stage` × 上一次操作的结果（新增一个
`lastResult`：`None` / `Ok` / `Fail`）。下面六个状态必须都能被这三项唯一确定，界面不许有
第七种长相。

记号：`运行` 指主操作区左边那个主按钮，`停止` 指它右边那个。

| 状态 | 主按钮 | 停止 | 菜单项 | 摘要行 | 日志区 |
|---|---|---|---|---|---|
| **A 空状态**（没打开工程） | 不显示；主操作区整个换成空状态引导（见 4.3） | 不显示 | 文件里只有`新建工程…` `打开工程…` `最近打开`可用；导出/清理/复制路径/打开日志文件全灰 | **隐藏**（没有结论可说，不留空行） | 只有启动横幅；不自动滚动 |
| **B 有工程 · 空闲 · 这次会话还没跑过** | `运行` 可用（主色） | 灰 | 全部可用 | 灰字一行：`还没运行过 · 按 F5 或点运行` | 只有启动横幅；不自动滚动 |
| **C 有工程 · 空闲 · 上次成功** | `运行` 可用（主色） | 灰 | 全部可用 | 绿字：`完成 编译 2.5 秒 · 用现成的库 · 8.6 MB`；作品已退出时追加 `· 作品已退出` | 保留上次全文；停在底部 |
| **D 有工程 · 空闲 · 上次失败** | `运行` 可用（主色） | 灰 | 全部可用 | 红字、可点：`失败 3 个错误 · 点这里看第一个` | 自动展开（紧凑模式下窗口自动长高，见 4.2）；视口滚到**第一条错误**那一行，不是底部 |
| **E 配置 / 编译中** | `运行` **灰**（见 2.2） | 可用 | `新建工程…` `打开工程…` `最近打开` 可用；`运行参数…`、两个导出、`清理` 全灰 | 灰字 + 秒数：`编译中 3.1 秒`（打包时 `生成应用程序中 …`，导出时 `导出工程中 …`） | 自动滚到底 |
| **F 作品运行中** | `运行` **可用**，文案不变（见 2.2） | 可用 | 同 E | 灰字 + 秒数：`运行中 作品在另一个窗口里 · 12 秒` | 自动滚到底（作品自己的输出在往里灌） |

补充约束：

- **状态切换不许让按钮换位置、换大小、换数量。** 变的只有"可用 / 不可用"和文案里的数字。
  唯一的例外是空状态 A（那时候"运行"无意义，见 4.3）。
- 摘要行只有一行，**不换行、不长高**。放不下就从右往左丢次要片段（先丢体积，再丢耗时），
  工程名和结论永远留着。
- 日志区的自动滚动：用户手动往上滚过之后就别再抢滚动条，直到下一次操作开始（`beginLog()`
  重置这个标志）。
- 「上次失败」里的"上次"指**这台机器上这次会话的上一次操作**，不跨进程持久化。启动时一律
  是 A 或 B。
- 摘要行里那句话是**上一次操作留下的结论**，状态表里写的文案是"没有结论时的默认值"。例如
  `清理` 之后状态回到 B，但摘要行显示的是「完成 清理 腾出 240 MB」而不是「还没运行过」——
  刚发生的事比一句套话有用。下一次操作会覆盖它。

### 2.1 导出 / 清理 属于哪个状态

- `导出应用程序…`：走 E（它真的在 configure + build），摘要行文案换成 `生成应用程序中`。
- `导出工程…`：也算 E，但它是**同步阻塞**的（`exportProject()` 会卡住界面几十秒）。进 E 之
  前必须先把摘要行和日志那一行画出来再开始干活（至少留一帧），否则用户看到的是一个假死窗口。
  这是已知缺口，记在第 7 节。
- `清理`：瞬间完成，不进 E；直接在摘要行报结果（6.3）。

### 2.2 「运行中」时主按钮怎么表现 —— 定了：**不变名、不置灰，按下去就是重跑**

做法：

- 状态 F（作品正在跑）下，`运行` 保持可用、文案还是「运行」。按它（或 F5）= 先掐掉正在跑的
  作品，再重新编译运行。日志里打一行「已停止上一次运行」，不弹任何确认框。
- 状态 E（正在 configure / 编译）下，`运行` 置灰。
- `停止` 在 E 和 F 都可用，其余状态灰。

理由：

1. **Processing 就是这么做的**：它的工具栏永远是 Run + Stop 并排两个按钮，Run 不会变成
   Stop；sketch 正在跑的时候按 Run 就是重启它。我们对标它，行为别拧。
2. **按钮变脸会毁掉快捷键的含义。** F5 必须永远是"让我看见我的作品"。如果主按钮在运行中
   变成「停止」，F5 的语义就得跟着状态漂移，学生按之前得先看一眼状态——这正好是我们要消
   灭的东西。
3. **运行中最常见的需求不是"停"，是"我改完了，再看一次"。** 现在的实现在这种时候只会回一
   句"上一个还在跑，先按停止"，把一次操作变成两次点击加一次阅读。
4. 代价可控：误触最坏的结果是作品重启一次。作品是子进程、没有未保存状态，代码在 VS Code
   里，什么都丢不了。
5. **编译中为什么反而置灰**：同一个构建目录并发跑两个 cmake 会把它搞坏，而"重新开始编译"
   对用户没有任何价值。要中断就用 `停止`，语义清楚。

实现上这需要一个"停掉之后接着重跑"的过渡意图（例如 `WB::pendingRun`），它**不是第七个状态**：
`kill()` 之后仍然走 `pump()` 正常收尾（退出码 -2），收尾时发现 `pendingRun` 就接着进 E。

## 3. 层级规则

**主操作区只放"一次循环里要用好几遍"的操作。** 只有两个：`运行`、`停止`。

**"一个作品用一次"的全部进菜单栏**：新建工程、打开工程、最近打开、导出应用程序、导出工程、
清理、运行参数、各类开关。

理由：写一个作品的过程里，`运行` 会被点几十上百次，`导出应用程序` 点 0~1 次，频率差两个
数量级。把它们并排摆成同样大的按钮，等于每次想运行都要先在四个同等权重的选项里挑一个——
制造选择困难，而且让"现在该点哪"这个问题每次都重新出现一遍。菜单栏的作用不是藏功能，是
**给频率排序**。

菜单树（三个菜单，和第 4 节的骨架图一致）：

```
文件
  新建工程…
  打开工程…
  最近打开        >       （最多 8 条，没有记录时整项置灰）
  ──────────
  导出应用程序…
  导出工程…
  ──────────
  清理
  ──────────
  复制工程路径
  复制输出
  打开日志文件
  ──────────
  退出

设置
  运行参数…
  ──────────
  [ ] 详细输出
  [ ] 紧凑模式
  [ ] 始终置顶

帮助
  环境自检                （把 --doctor 的输出打进日志区）
  关于 Easel              （版本行 + 启动横幅那几项）
```

摆位依据：

- `清理` 紧跟在两个导出之后、单独一组——IDE 里 Clean 都是和 Build / Export 同一个菜单的邻居
  （VS 的「生成」菜单、Xcode 的 Product、IntelliJ 的 Build）。**不许放进二级子菜单**：它现在
  是"构建目录坏掉了"唯一的界面出路（6.3），找不到就等于没有。
- `复制工程路径` `打开日志文件` 是"拿去别处用"的一组，放一起。
- `环境自检` 进帮助，不进设置：它什么都不改，只是报告。
- **菜单里只显示真的实现了的快捷键。** 本轮只有一个：`运行` = F5（现有承诺，文档里已经写过）。
  不许在菜单项右边摆 `Ctrl+N` 这种没接上的装饰——界面上写出来的快捷键必须按下去就有反应。
  `停止` 和 `新建 / 打开` 暂不给快捷键：`App::onKey` 只给单键，组合键要在回调里自己拼
  `keyDown(LeftCtrl)`，本轮不值得（已知缺口，第 7 节）。

## 4. 两种模式

同一套骨架，**紧凑模式就是把最后一段（日志区）收起来**。不许出现只在某一个模式里存在的
控件或另一套布局代码。

### 4.1 完整模式（默认，960×600 逻辑像素）

```
┌─────────────────────────────────────────────────┐
│ 文件  设置  帮助                                 │  菜单栏（ImGui 自己的高度）
├─────────────────────────────────────────────────┤
│ MySketch   ~/projects/MySketch   [ ]置顶  [收起] │  工程栏 kProjectH=48
├─────────────────────────────────────────────────┤
│                                                 │
│   [ 运行  F5 ]        [ 停止 ]                   │  主操作区 kActionH=76
│                                                 │
├─────────────────────────────────────────────────┤
│ 完成 编译 2.5 秒 · 用现成的库 · 8.6 MB           │  摘要行 kSummaryH=34（单行）
├─────────────────────────────────────────────────┤
│ 输出           [ ]详细输出  清空输出  [收起]      │  日志区工具条
│ [ 0.0s] 工程 /Users/…/MySketch                  │  日志区（吃掉剩下的全部高度）
│ [ 2.5s] 编译完成 -> bin/app                      │
└─────────────────────────────────────────────────┘
```

- 从上到下是一条直线：**哪个工程 → 点哪里 → 怎么样了 → 凭什么**。不许往这条线里插别的东西。
- 工程栏：工程名用 T1 字号、正常前景色；完整路径用 T3 字号 + `th.muted`，**弱化**，它是给
  "我是不是打开错了"一眼核对用的，不是主角。路径点一下复制（和菜单里的 `复制工程路径` 同一
  个动作，同一个名字）。
- 工程栏右侧只放两个东西：`始终置顶` 勾选、日志区的 `收起 / 展开`（= 紧凑模式开关，和菜单里
  那一项是**同一个状态**，不是两个）。
- 主操作区：两个按钮左对齐，之间留 S4。不在这里放第三个控件，**包括运行参数输入框**（它进
  `设置 → 运行参数…`；当前参数非空时在工程栏末尾用 T3 灰字显示 `参数：--open data/x.json`，
  免得学生忘了自己设过参数而困惑）。
- 摘要行：单独一段，自己一行，和日志区之间有分隔线。**日志是证据，摘要是给人读的结论**，两
  者不许互相替代。
- 底部状态栏（`App::statusBar`）**关掉**：它显示状态灯 / 状态文字 / 缩放倍数，前两项和摘要行
  是同一件事的两份事实来源，缩放倍数对工具类程序没意义。状态只由摘要行说。

### 4.2 紧凑模式（520 × 按内容算出来的高度）

- 组成：菜单栏 + 工程栏 + 主操作区 + 摘要行。日志区收起。
- 默认宽 520。**高度不写死 300**，按各段实际高度加起来算（`kMenuH + kProjectH + kActionH +
  kSummaryH + 3 条分隔线 + 2×WindowPadding.y`，dpi=1 时约 236）。写死一个比内容高的数会在
  底部留一块无解释的空白，看着像没做完。
- **只有失败（状态 D）时自动长高**把错误行展开：高度 = 紧凑高度 + 错误段（最多 6 行，每行
  T3 行高）+ 段内留白，上限 420。成功不长高——每次编译窗口都跳一下比少看几行更烦人。
- 长高是"临时"的：回到 B / C 状态时收回原高度。
- **自动改窗口大小只发生在"切模式"和"进 / 出失败状态"这两个时刻，而且是一次性的**（实现里
  是一个 `fitFrames` 计数，贴合完就停）。之后用户怎么拖窗口都不管；发现当前高度和我们上次
  设的对不上（差 > 2 像素）就认定用户插手过，这一轮不再动它。
- 紧凑模式带 `始终置顶` 开关（`glfwSetWindowAttrib(win, GLFW_FLOATING, ...)`），但置顶**不是**
  紧凑模式的一部分：两个开关各自独立，完整模式也能置顶。

### 4.3 空状态（状态 A，新用户的第一屏）

```
┌─────────────────────────────────────────────────┐
│ 文件  设置  帮助                                 │
├─────────────────────────────────────────────────┤
│ 还没有打开工程                   [ ]置顶  [收起] │  工程栏（路径行空着，不画）
├─────────────────────────────────────────────────┤
│   先新建一个工程，或者打开一个已有的              │  T2
│   [ 新建工程… ]   [ 打开工程… ]                  │  主操作区（按钮同主按钮尺寸）
│   最近打开：MySketch · Sort · Demo               │  T3 灰字，可点，最多 3 条
├─────────────────────────────────────────────────┤
│ 输出   …                                        │  日志区：只有启动横幅
└─────────────────────────────────────────────────┘
```

- 摘要行隐藏。
- 空状态的主操作区**按内容取高**（比两颗按钮那一档高一行多），不套 `kActionH`：它比别的状态
  多一行引导语和一行最近打开。其余三段的高度档位照旧。
- 这是"主区只放高频操作"的**唯一例外**，理由写死在这里：空状态下 `运行` 没有任何可运行的东
  西，摆两个灰按钮等于给新用户一条死路；而此刻"新建 / 打开"就是唯一的循环内操作，它们在这
  一屏里是高频的。一旦有了工程，主区立刻换回 `运行` / `停止`，这两个按钮不再出现在主区。
- 空状态下日志区保留并展开：启动横幅是"环境有没有问题"的唯一现场证据，第一屏就该看得见。

### 4.4 记进 `workbench.json` 的东西

文件位置不变（`exeDir()/workbench.json`）。新增字段，缺字段一律用默认值，解析失败整块丢掉：

```json
{
  "recent": ["..."],
  "window": { "x": 120, "y": 80, "w": 960, "h": 600, "compact": false, "alwaysOnTop": false },
  "verbose": false
}
```

- `w/h` 存的是**完整模式**的尺寸（紧凑模式的高度是算出来的，不存）。
- `x/y/w/h` 直接存 `glfwGetWindowPos/Size` 给的屏幕坐标原值，**不做 dpi 换算**。存什么还什么，
  换显示器时不会被二次缩放。
- `verbose` 存"详细输出"开关。**运行参数不存**：它是临时的，存下来会让"下次打开莫名带着参数
  跑"变成一个看不见的状态。
- 退出时写一次即可（窗口尺寸每帧都在变，别每帧写盘）。

### 4.5 还原前必须检查"这个位置现在还看得见"

换了外接屏、拔掉外接屏、换分辨率之后，上次的位置可能落在任何显示器之外。

**分工（写死，免得出现第二份夹取逻辑）：**

| 谁管 | 管什么 |
|---|---|
| `src/backend.cpp`（别人的地盘） | **尺寸**：`computeWindowGeometry()` 已经会把请求的尺寸等比夹进显示器可用区域（留 8% 边距），`centerWindow()` 算上标题栏厚度居中。工作台**不得**重复这件事 |
| `workbench/main.cpp`（这份规范） | **位置能不能用**：只回答"上次存下来的 `x/y` 在现在这套显示器上还看得见吗"，答案只有"用"或"不用"，**不修正、不夹取** |

还原顺序：

1. 尺寸：把存下来的 `w/h` 交给 `App::size()`，在 `run()` 之前设好。backend 会替我们夹。
   工作台这边只做一次下限保护（不小于最小尺寸：完整 760×420，紧凑 440×200），上限不管——
   那是 backend 的活。
2. 位置：窗口起来之后再判断一次。窗口顶部那条"标题栏带"（窗口矩形顶部、高 32 逻辑像素）
   必须和某个显示器可用区域（`glfwGetMonitors()` + `glfwGetMonitorWorkarea()`，GLFW 3.4 有）
   相交，且交集宽 ≥ 120、高 ≥ 24。**只验这条带**：能抓住标题栏，用户就能把窗口拖回来。
3. 验过了才 `glfwSetWindowPos()`；**验不过就什么都不做**——窗口留在 backend 居中好的位置。
   不要试图把它"挪"到某个角落，那就是在写第二份夹取逻辑。
4. 给窗口设最小尺寸（`glfwSetWindowSizeLimits`），免得用户手动拖到布局塌掉。

这条"只判断、不修正"的切法就是和 backend 不重叠的保证：backend 回答"多大、放哪"，工作台
只回答"上次那个位置还算数吗"。

**工作台怎么拿到窗口句柄**：`glfwGetCurrentContext()`（OpenGL 后端下就是主窗口；`workbench`
经 `easel_imgui` 间接链接 glfw 3.4，头文件可直接 include）。DX11 后端下它返回 `nullptr`，
此时窗口几何 / 置顶 / 紧凑模式的"改窗口大小"整体降级（位置不还原、菜单项置灰），界面布局本身
不受影响。**这是临时手段**，正式做法是 `App` / `internal::backend` 暴露窗口句柄（第 7 节）。

## 5. 视觉档位

定完这一节之后，`workbench/main.cpp` 里**不许出现规范外的魔法数**。所有尺寸写成
`kXxx * dpi`（`dpi` 就是 `draw()` 收到的那个参数），常量集中在文件顶部一个 `Metrics` 块里，
名字和下表一一对应。

现有的 `Theme`（`include/easel/theme.h`）已经有的东西**一律复用，不另造**：
`accent` / `accent2` / `fg` / `muted` / `good` / `warn` / `bad` / `surface` / `bg` / `radius` /
`fontSize`。`src/theme.cpp` 的 `applyTheme()` 已经设过全局 `WindowPadding(14,12)`、
`FramePadding(10,6)`、`ItemSpacing(9,8)`、各类 `Rounding = radius`，并且 `App` 启动时对整张
style 调过 `ScaleAllSizes(dpi)`——**这些不要再改、也不要在工作台里覆盖**，下面的档位是和它们
对齐过的。

### 5.1 间距（逻辑像素，用时乘 dpi）

| 档 | 值 | 用在哪 |
|---|---|---|
| `kGapTight` | 6 | 同一组里贴着的两个元素（工程名和它右边的参数提示） |
| `kGap` | 10 | 一般元素间距（≈ 全局 `ItemSpacing.x`） |
| `kPad` | 14 | 段内左右留白（= 全局 `WindowPadding.x`，段和窗口边对齐） |
| `kGapSection` | 20 | 两个按钮之间、段内上下呼吸 |

段与段之间不用间距值，用**一条分隔线**（`ImGui::Separator()`）。全界面只有三条：工程栏下、
主操作区下、摘要行下。不许加第四条。

### 5.2 段高（逻辑像素）

| 档 | 值 | 说明 |
|---|---|---|
| `kProjectH` | 48 | 工程栏（两行文字：工程名 T1 + 路径 T3） |
| `kActionH` | 76 | 主操作区（按钮 44 + 上下各 16） |
| `kSummaryH` | 34 | 摘要行（单行，永不长高） |
| `kBtnH` | 44 | 主按钮 / 停止 / 空状态的两个按钮，高度统一 |
| `kBtnRunW` | 168 | `运行`（含 F5 提示） |
| `kBtnStopW` | 112 | `停止` |
| 日志区 | 剩下全部 | 不设固定值 |

### 5.3 字号（全部写成 `ImGui::GetStyle().FontSizeBase * 系数`，别写绝对像素）

| 档 | 系数 | 用在哪 |
|---|---|---|
| T1 | 1.25 | 工程名（现在的 1.5 在 960 宽里过大，压到 1.25） |
| T2 | 1.00 | 正文、菜单、摘要行、按钮文字默认 |
| T2b | 1.15 | 只给主按钮 `运行` 的文字 |
| T3 | 0.92 | 路径、参数提示、次要说明、日志区（等宽，`monoFont()`，沿用现值） |

只有这四档。**不许出现第五个系数。**

### 5.4 圆角

- 只有两个值：`th.radius`（按钮、输入框、子窗口，全局 style 已经设好，照用）和 `0`（分隔线、
  摘要行这种贴边的色块）。
- 不要为某个控件单独调圆角。

### 5.5 主色只用在一个元素上

**`th.accent` 在工作台里只允许出现在一个地方：主按钮 `运行` 的填充色。**

- `运行` 按钮：底色 `th.accent`，hover / active 走全局 style 已有的 `ButtonHovered/Active`。
  其余按钮一律用默认的 `th.surface` 系底色。
- **置灰的时候不涂主色**（状态 E）：只靠 ImGui 的 `DisabledAlpha` 半透明太弱，一个绿按钮
  半透明了还是绿的，看不出来按不按得动。灰了就用普通按钮底色。
- 摘要行颜色只用语义色：成功 `th.good`、失败 `th.bad`、警告 `th.warn`、中性 `th.muted`。
- 日志区：错误 `th.bad`、警告 `th.warn`、普通输出 `th.fg`、**我们自己打的那些行（`kind==3`）
  从 `th.accent` 改成 `th.muted`**——它们是旁白，不是重点；结论已经由摘要行说了。这样主色在
  整个界面里就真的只剩一处，视线第一眼一定落在 `运行` 上。
- `th.accent2` 工作台不用（它是给作品的图表用的）。

### 6.2 两个导出的确认框（极简，不是向导）

- `导出应用程序…`：一句话说明（"编一个优化过的版本，连同 assets / data 放进下面这个目录，
  可以直接双击运行"）+ 目标路径（`<工程>/dist/<名字>-release`）+ 一句"要重新编译一遍，大约
  几十秒"+ `导出` / `取消`。不给选目录（`packageInto()` 写死在 `dist/` 下）。
- `导出工程…`：一句话说明 + 目标路径（默认 `<工程>/dist/<名字>`，`ExportOptions::outDir`
  本来就支持改）+ `选目录…` + 一句"几十 MB，界面会卡一下" + `导出` / `取消`。
- 两个框都只有一屏、不滚动、不带选项清单。省略号的存在感到此为止。

### 6.3 清理

**要删的（只有这两个，路径必须调 `buildDir()` / `releaseDir()` 拿，不许照抄字符串）：**

| 删 | 新式工程（`.easel/CMakeLists.txt` 在） | 老式工程（根目录有 `CMakeLists.txt`） |
|---|---|---|
| 平时编译的构建目录 | `<工程>/.easel/build` | `<工程>/build/<preset>` |
| 交付版的构建目录 | `<工程>/.easel/build-release` | `<工程>/build/release` |

**绝对不删的：**

- `<工程>/dist/` —— 那是 `导出应用程序` / `导出工程` 的**产出，是交付物，不是垃圾**。删掉它
  等于把学生刚做好、准备交上去的东西清掉，而且它不一定还能原样重新生成（导出时的 Easel 版
  本、assets 都可能已经变了）。Xcode 的 Clean 也不会动你的 Archives。
- `<工程>/.easel/last-build.log` —— 上一次失败的现场证据，清理构建产物不该顺手毁掉它。
- 学生自己的任何文件（`src/`、`data/`、`assets/`、`tests/`）—— 清理只碰"能由编译重新生成的
  东西"，这是它的定义。
- `.easel/` 下除上面两个 build 目录以外的任何东西（`CMakeLists.txt` 等脚手架是工程的一部分）。

**为什么值得放在容易找到的地方：** 它顺带解决一个真实故障——configure 失败会留下一个
"有 `CMakeCache.txt` 却没有 `build.ninja`/`Makefile`"的半成品构建目录（`buildConfigured()`
就是为这个写的）。我们虽然让这种情况能自动重配，但构建目录还有别的损坏方式（换过编译器、
磁盘写坏、手工动过）。有了 `清理`，用户不用开终端、不用自己找那个藏在 `.easel/` 里的目录、
不用知道什么是 CMakeCache，就有一条出路："清理，再运行"。这条出路必须一眼能找到，所以
`清理` 在 `文件` 菜单第一层，不进任何子菜单。

**不弹确认框。** 和 VS / Xcode / IntelliJ 一致：删的是可以重新生成的东西，代价只是下次编译
慢一点（有现成的库时也就几秒），为它加一次点击不划算。分寸靠另外三件事给：

1. 菜单项上挂 tooltip，点之前就说清楚删哪两个目录、现在多大（例如"删掉 .easel/build 和
   .easel/build-release，现在约 240 MB；不会动 dist/ 和你的代码"）。大小算不出来时不显示数字，
   不要显示 0。
2. 删完在摘要行报告：`完成 清理 腾出 240 MB`（绿字，走状态 C 的长相），同时在日志里逐行列出
   真正删掉的目录。
3. 忙的时候（状态 E / F）菜单项置灰——正在编译时删构建目录必炸。

**清理之后的状态：** 回到状态 B（"这次会话还没跑过"），`lastResult` 重置为 `None`。理由：上
一次编译的结论已经不成立了，继续挂着"完成 2.5 秒"是在说谎。日志区不清空（`清空输出` 是另一
个动作，两者别合并）。

**命令行：`easel --clean <工程目录> [--json]`**

- 和界面同名（用词一致，1.1），和 `--build/--run/--package/--export` 对称：`"clean"` 加进
  `kValueFlags`（带值的那张表），`usageText()` 里补一行，参数说明里提一句"不会删 `dist/`"。
- 走和它们一样的前置校验（`headless::resolveProject()`）——但 `清理` 不需要 cmake，
  所以这里要么单独校验（目录存在 + 是工程），要么给 `resolveProject()` 加一个"不要求 cmake"
  的开关。**不要为了省事而让"没装 cmake 就不能清理"**，那正好是最需要清理的场景之一。
- 文本输出：横幅 + 每个删掉的目录一行 + 一行"腾出 240 MB"。
- `--json`：`{"ok":bool, "action":"clean", "project":"...", "removed":["...","..."],
  "bytes":<腾出的字节数>, "error":"..."}`。目录本来就不存在不算失败（`ok:true`，
  `removed` 空，`bytes:0`）——幂等，脚本里敢连着调两次。
- 实现只用现成的东西：`removeTreeU8()` 删、`listDirU8()` + `fileStamp()` 递归算大小、
  `formatBytes()` 格式化。GUI 和无头共用同一个函数，别写两份。

### 6.4 文档 / 截图用的启动钩子（不是给学生的功能）

界面状态大多要点一下才出得来，截图和冒烟测试没法点。两个环境变量负责把界面开到某个状态，
**只在启动时看一眼，不改变任何行为，也不往界面里塞假数据**（"失败"那张图是真的编译失败）：

| 变量 | 作用 |
|---|---|
| `EASEL_WB_ARGS=…` | 启动时把运行参数填进去，等价于在「设置 → 运行参数…」里手填 |
| `EASEL_WB_AUTORUN=…` | 启动后自动点一次：`run`（运行）、`clean`（清理）、`doctor`（环境自检）、`new`、`exportapp`、`exportproject`、`runargs`、`about`（后五个是打开对应的对话框） |

为什么不做成命令行参数：工作台的参数表是给学生和脚本看的，多一个只有我们用的开关就是多一
行噪音；而且 `--help` 里出现一个「自动点一下某个菜单」的参数，解释成本比它的价值高。

## 7. 已知缺口（规范留下的账，不在本轮解决）

1. `App` / `internal::backend` 不暴露窗口句柄，工作台只能用 `glfwGetCurrentContext()` 拿
   （DX11 后端下拿不到，位置还原 / 置顶 / 改窗口大小整体降级）。需要的接口形状，两个里给一个
   就够：
   - `GLFWwindow* internal::backend::window();`（最小改动，工作台已经 include 得到 glfw），或
   - `bool internal::backend::visibleWorkArea(int x, int y, int w, int h);`
     （"这个窗口矩形还看得见吗"，只判断不修正）+ `internal::backend::setWindowRect/ setFloating`。
   顺带：`src/backend.cpp` 里已有的 `computeWindowGeometry()` / `centerWindow()` 目前在匿名
   命名空间，工作台用不到也不该复制——这两个函数管"多大、放哪"，暴露出来之后工作台那条
   "只判断不修正"的位置检查可以整条删掉。
2. `exportProject()` 同步阻塞几十秒，界面在这期间假死。应该和编译一样走子进程 / 异步。
3. `停止` 没有快捷键（`App::onKey` 只给单键，Processing 用的是 `Ctrl+.`）。
4. `src/export_project.cpp` 的检查清单用 `[√]`，`√` 不在内置字体子集里，会显示成豆腐块。
5. 启动横幅和日志里的内部词汇（1.6 那张表）还没换，学生仍然会看到"预编译""abi""配置中"。
6. `workbench.json` 写在 `exeDir()` 下，装在只读位置（`.app` bundle、系统目录）时存不下窗口
   几何和最近列表。
7. 紧凑模式切换是直接改窗口大小（`glfwSetWindowSize`），尺寸是我们自己算的小数值（520 宽），
   没有过 backend 的"夹进可用区域"那一步。在可用高度小于 240 的极端配置上可能超出；要彻底
   解决得等第 1 条的接口。
